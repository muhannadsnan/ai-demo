That last row is the useful one. Your network reaches the vendor fine; the 401 is simply "no credential presented". Nothing is blocked at the firewall. The only missing piece is the key itself, which is a conversation with your company rather than an engineering problem.

So the demo does not wait for it

The project ships with an offline provider as the default. It fakes the language model and nothing else — the routing, validation, streaming, chunking, embedding and ranking are all genuine. You can read, run and understand the entire integration today, and switching to a real backend later is one line in .env with zero application code changes.

And if you want a real model this week without waiting on anyone: install Ollama, pull llama3.2, set NUXT_AI_PROVIDER=ollama. Free, local, private, and it exercises exactly the same code path the paid vendor will.

02 The one rule worth memorising

Every AI feature you ever build should have this shape. The browser talks to your server; only your server talks to the model vendor.

03 Demo one · streaming chat

The smallest complete AI feature. Underneath the vocabulary, a chat model is one HTTP endpoint that takes a list of messages and returns another message: 

POST https://api.openai.com/v1/chat/completions
Authorization: Bearer sk-...

{
  "model": "gpt-4o-mini",
  "messages": [
    { "role": "system",    "content": "You are a helpful assistant." },
    { "role": "user",      "content": "What is an embedding?" }
  ],
  "temperature": 0.3,
  "max_tokens": 800,
  "stream": true
}

That is the entire API you were blocked from two years ago. The demo calls it with plain fetch and no SDK — deliberately, because the transferable knowledge is the HTTP contract, and that is what you will re-implement in CodeIgniter with cURL.

Three things that surprise everyone

The model has no memory. It is a pure function of the messages you send. A conversation feels continuous only because the client resends the whole history every turn. Which means turn 20 pays for turns 1–19 again — cost grows quadratically with conversation length, and trimming that history is your decision, not the vendor's.

The system prompt must come from your server. The demo rejects any system message sent by the browser. If the client can set it, the client can replace your instructions with anything. Treat it exactly like a price field in a shopping cart.

Streaming breaks in a specific way. TCP splits wherever it likes, so a chunk can end mid-JSON. Both the server parser and the browser parser keep a buffer and only process up to the last complete boundary. Skip that and it works perfectly on localhost, then corrupts intermittently in production — the worst failure mode there is.

And one that costs money

If the user closes the tab, generation continues and you keep paying for tokens nobody will read. chat.post.ts listens for req.on('close') and aborts. Four lines; do not skip them.

04 Demo two · search over your own documents

You asked what the "todo list app" of AI search is. This is it: retrieval-augmented generation over documents you own — usually sold as "chat with your docs". Nearly every AI product with a search box is an elaboration of it.

The problem it solves: the model has never seen your internal handbook. Ask it about your Integration Bus retry policy and it will either say it does not know, or produce a fluent, confident, entirely invented answer. The fix is not to retrain it. The fix is to find the relevant passages yourself and paste them into the prompt.

Why retrieval and not fine-tuning

Fine-tuningRetrieval (RAG)
What it changesthe model's weightsthe prompt
Updating one factretrainedit the file, re-index
Can cite sourcesnoyes
Skills neededML engineeringbackend engineering
Good at teachingstyle, format, behaviourfacts

For "answer questions about our documents", retrieval wins on every row that matters. Fine-tuning is for when you need a model to consistently behave a certain way, not when you need it to know something.

Chunking is where quality is won or lost

Why not embed a whole document? Because one vector then has to represent everything the document says, and ends up representing nothing in particular. Too large and the relevant sentence is diluted; too small and the answer splits across two chunks so neither looks relevant on its own. The demo splits on the document's own headings first, then caps at ~900 characters with a small overlap.

One trick worth stealing: each chunk's embedded text is prefixed with DocTitle > Heading. The heading words end up inside the vector, so a chunk under ## Retry policy is findable by the word "retry" even when its body never repeats it.

05 The numbers, and why you must measure them

Cosine ranking always returns your top K — even when nothing in the corpus is relevant. It has no concept of "no good answer". Skip that check and an off-topic question quietly gets answered from the three least-irrelevant passages, complete with citations. That is how a RAG system starts inventing things while looking rigorous.

So the demo ships an evaluation suite: twelve golden question → expected-document pairs, plus deliberately unanswerable questions to establish the noise floor. Here is the real output of npm run eval on this machine:

Genuine matches land between 0.09 and 0.36. Off-topic questions top out at 0.064. The relevance floor sits at 0.07, in the gap — and that gap is uncomfortably narrow. That narrowness is itself the lesson: it is a fair picture of what a purely lexical embedder can do, and a real embedding model separates the two far more cleanly. Which is most of what you are paying for.

The habit to form

These constants are empirical and specific to this corpus and this embedder. Never copy someone else's threshold. Re-measure whenever you change the model, the chunk size or the documents — and put the eval in CI, because it already exits non-zero on regression. Twelve golden questions will catch more real problems than any amount of eyeballing.

The other metric on that report is recall@k — was the right passage anywhere in the top K. It is the one that caps your quality, because a passage that is never retrieved can never be cited, however good the model is.

06 Switching backends

One line in .env, restart, done. No application code changes — that is the entire point of the provider abstraction in server/utils/ai/.

NUXT_AI_PROVIDERNeedsCostWhat you get
mock nothingfree Real retrieval and streaming; replies are extractive, not generated
ollama Ollama installedfree A real language model, running on your own machine
openai an API keypaid The real thing

The test of whether the abstraction sits in the right place: the application code above it cannot tell which implementation is running. chat.post.ts and ask.post.ts contain no vendor names, no model names, no URLs and no keys. Preserve that property and swapping vendors stays a config change forever.

Misconfiguration is handled explicitly too. Set openai without a key and every endpoint returns a 503 that names the exact variable to set, rather than a bare "Server Error" — worth doing, because that is the error you will hit first.

The bridge to what you already do

An embedding pipeline is structurally identical to your partner file imports: fetch, parse, chunk, batch, skip-if-hash-unchanged, promote in a transaction, log rejects for retry. You have written that shape many times. The only new failure mode is a vendor returning 429, which you handle exactly like a partner rate limit.

Then, in rough order of value

  1. Replace knowledge/ with real documents from one of your systems and re-run the eval. Watching retrieval quality change on material you know well is the fastest way to build judgement about chunking.
  2. Install Ollama and run the same queries. The difference between lexical and real semantic matching is the single most instructive five minutes here.
  3. Port the search endpoint to CodeIgniter against a real table. That is your actual first production task, and docs/04 is written for it.
  4. Add hybrid search — combine embedding similarity with your existing MySQL FULLTEXT scoring. Usually the largest single quality win available, because embeddings are weak exactly where keyword matching is strong: identifiers, error codes, table names. Your FULLTEXT index is not a worse version of this; it is the other half of it.
  5. Only then look at tool use and agents. They are much easier to reason about once the pieces above are second nature.
Before any of it touches customers

Five things, in order: authentication and per-user quotas; a budget alert set at the vendor on day one; token and cost logging per request; never letting model output cause a side effect without a deterministic check in between; and the eval running in CI. Those five separate "we shipped an AI feature" from "we shipped an AI incident".
