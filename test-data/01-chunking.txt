Order Service > Purpose

Order Service owns the lifecycle of an order after it has been accepted by Core.
Core remains the system of record for pricing and invoicing; Order Service is
the system of record for fulfilment state.

Order Service > Order states

An order moves through these states, in this order:

1. `received` — created by Core, not yet validated
2. `validated` — address and stock checks passed
3. `picking` — assigned to a warehouse
4. `dispatched` — handed to a carrier, tracking number issued
5. `delivered` — carrier confirmed delivery
6. `closed` — invoiced and reconciled

Two terminal exception states exist: `cancelled` (before dispatch) and
`returned` (after delivery). An order can never move backwards. Attempting an
invalid transition returns HTTP 409 with an error code of `invalid_transition`.

Order Service > API

The service exposes a REST API at `https://orders.internal.nordvik.no/v2`.
Authentication uses a service token in the `Authorization: Bearer` header;
tokens are issued by Core and expire after 24 hours.

Key endpoints:

- `GET /orders/{id}` — full order with current state and history
- `POST /orders/{id}/transition` — request a state change
- `GET /orders?updated_since=` — incremental sync, max 500 per page
- `POST /orders/{id}/cancel` — cancels if state is before `dispatched`

The API is versioned in the path. Version 1 was retired in March 2023 and any
remaining v1 traffic is rejected with HTTP 410.

Order Service > Rate limits and timeouts

Clients are limited to 600 requests per minute per token. Exceeding this returns
HTTP 429 with a `Retry-After` header in seconds. The internal HTTP timeout when
Core calls Order Service is 5 seconds for reads and 15 seconds for transitions.

Order Service > Known issues

The `updated_since` cursor uses a timestamp with one second resolution. Orders
updated within the same second as the cursor boundary can be returned twice.
Consumers must therefore be idempotent. This is documented behaviour, not a bug
that will be fixed, because changing it would require a table rewrite of
`order_events`, which currently holds about 400 million rows.
